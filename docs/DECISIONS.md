# DECISIONS

## ADR-001：在进程内接管，而不是搭本地网关

- 日期：2026-09-27
- 状态：已采纳
- 背景（遇到了什么问题）：
  Typora 的许可证密文只能用官方私钥签发。要让本地校验通过，要么让服务端认可本机，
  要么让客户端接受我们的返回值。常见做法是替换内置公钥 + 用 hosts 把激活域名指到本地服务器
  （本仓库早期版本就是这么写的）。
- 考虑过的方案：
  1. 网关方案：生成新 RSA 密钥对，替换字节码里的公钥，hosts 重定向到本地 HTTP 服务器；
  2. 注册表 / 试用期重置：改 `IDate` 反复续 15 天试用；
  3. 进程内接管：Hook 明文入口 `launch.dist.js`，直接改解密与网络调用的返回值。
- 决策：采用方案 3。
- 为什么选这个：
  - 公钥在 V8 字节码的常量池里，替换它要精确改字节码，且会破坏 `cachedData`；
  - hosts + 本地服务器需要常驻进程、要动系统配置、还要处理证书，副作用面大且难回滚；
  - 方案 3 的全部改动都落在 asar 内一个明文文件里，`--restore` 一次拷贝就能完全回退，
    且不产生任何常驻组件。
- 为什么不选其他：
  - 方案 1 的收益与方案 3 相同（都是让客户端认可），代价却高得多；
  - 方案 2 在本版本上被证伪：把 `IDate` 改成当天后 `trailRemains` 仍为 0，
    说明试用期另有隐藏记账点，重置无效。
- 后果：
  - 补丁与 Typora 版本强绑定，换版本要重新核对注入点与自校验量（脚本会重新计算，不会静默出错）；
  - 必须额外处理自校验，否则程序启动 1 秒后自杀（见 ADR-003）。
- 何时重新审视：Typora 把关键逻辑从 `launch.dist.js` 移走，或字节码入口不再是明文时。

## ADR-002：伪造许可证解密结果，而不是伪造注册表内容

- 日期：2026-09-27
- 状态：已采纳
- 背景（遇到了什么问题）：
  注册表里的 `SLicense` 必须是能用官方公钥解开的密文。既然拿不到私钥，注册表里就永远写不出「真」值。
- 考虑过的方案：
  1. 反复尝试构造能被解开的密文（本质是在没有私钥的情况下伪造签名，不可行）；
  2. Hook 注册表读取模块（`native-reg` / `child_process`），返回预置值——但预置值仍然要能解密；
  3. Hook `crypto.publicDecrypt`，让解密这一步直接返回我们构造的许可证 JSON。
- 决策：采用方案 3。
- 为什么选这个：
  - 本地校验只要求「解密结果能解析成 JSON」，**且 `fingerprint` 与客户端自己算的那份逐字符相等**；
    其余字段（`email` / `date` / `version` / 许可证号）不比对——逐项改成无意义值后仍 `[L] pass`；
  - 只需要一个 Hook，且对「用户本来就有真许可证」的情况可以放行（先试真解密，成功就返回原值）。
- 更正记录（2026-09-28）：本 ADR 最初写的是「不比对 `fingerprint`」，**这条是错的**。
  当时的对照实验只改了 `email` / `date` / `version` / 许可证号，漏了 `fingerprint`；
  而研究机算出的指纹恰好不含特殊字符，于是被误判成「不校验」。用只改 `fingerprint` 的对照实验
  一票证伪。教训：**「没被校验」的结论必须对着每一个字段各做一次对照**，
  不能把「改了其中几个都没事」当成「全都不校验」。
- 为什么不选其他：
  - 方案 1 在密码学上不成立；
  - 方案 2 控住了输入却控不住密钥，绕不开同一堵墙，还多一层依赖。
- 后果：
  - 注册表里的 `SLicense` 变成了一个「信号值」，其内容不再具有密码学意义；
  - 需要同时接管续期（ADR-004），否则服务端会把这个假值判死。
- 何时重新审视：若上游开始在本地校验里加入签名绑定（例如校验许可证号与机器指纹的关联）。

## ADR-003：在 `crypto.createHash` 上放行自校验

- 日期：2026-09-27
- 状态：已采纳
- 背景（遇到了什么问题）：
  Typora 启动约 1 秒后会读取 `package.json` 的 `main` 指向的文件（即被我们改过的
  `launch.dist.js`），算 sha256 与内置基准比对，不一致就写 `[LC] Integrity check failed` 并退出。
- 考虑过的方案：
  1. 让补丁后的文件恰好等于原文件（不可能，内容变了哈希就变）；
  2. 从 `page.json` 的 `main` 换指到新文件——但校验读的就是 `main`，换了文件基准就对不上；
  3. 伪造读取结果：Hook `fs.promises.readFile`，读到 `launch.dist.js` 时返回原始内容；
  4. 伪造哈希结果：Hook `crypto.createHash`，命中这次计算时让 `digest()` 返回原始文件的 sha256。
- 决策：采用方案 4。
- 为什么选这个：
  - 只需内嵌 64 个十六进制字符，不需要在补丁里塞进整个原始文件（方案 3 需要内嵌 1383 B 的原文）；
  - 命中判据（**补丁后的字节长度 + 原始文件前 48 字符**）足够独特，不会误伤其他哈希调用
    （实测确认 `[hash:sha256] ["…guid…","typora"]` 这类指纹计算不受影响）；
  - `digest(enc)` 支持任意编码回传，无论调用方要 hex 还是 base64 都能对上。
- 为什么不选其他：
  - 方案 3 也被验证可行，但把整个原始文件塞进补丁会显著增大注入体积，且要 hook 三个 fs API 更易漏；
- 后果：
  - 需要内嵌入口文件的 base64 原文与 sha256，补丁体积增大到 ~11KB（可接受）；
  - 长度必须定宽回填：先用 8 个 0 占位、量出真实长度后再替换成同宽数字，否则第二次替换会改变文件长度；
  - `src/patch.ts` 会在渲染后断言「长度占位符只出现一次」，模板里任何地方重复书写占位符都会立刻报错。
  - 后续演进见 ADR-006：识别判据从「文件头」改成了「长度 + 补丁标记」，并补上了读取层兜底。
- 何时重新审视：上游把自校验换成非 sha256、或不再校验 `main` 指向的文件时。

## ADR-004：接管 `electron.net.request` 而不是 `electron-fetch`

- 日期：2026-09-27
- 状态：已采纳
- 背景（遇到了什么问题）：
  续期失败会把 `hasL` 打回 false，所以续期必须「成功」；更新检查会替换 `app.asar` 让补丁失效，
  所以更新请求必须被拦。需要选一个拦截层面。
- 考虑过的方案：
  1. Hook `electron-fetch` 的导出函数；
  2. Hook `electron.net.request`，返回一个假的 `ClientRequest`；
  3. 让请求真的发出去，只改响应。
- 决策：采用方案 2。
- 为什么选这个：
  - `electron-fetch` 是 asar 外的依赖，模块解析路径随打包方式变化，`require` 到同一实例不保险；
  - `electron.net.request` 是两条链路（续期、更新）的公共汇合点，一次 Hook 全覆盖；
  - 完全不出网，`--restore` 后不留任何痕迹。
- 为什么不选其他：
  - 方案 1 依赖模块解析细节，脆；
  - 方案 3 仍然要连服务端，且服务端一定会拒绝假许可证。
- 后果：
  - 假响应的 `res` 必须是真正的 `stream.Readable`：`electron-fetch` 内部执行 `res.pipe(body)`，
    只给 `EventEmitter` 会抛 `FetchError: Invalid response: res.pipe is not a function`
    （这个坑踩过一次，记录在此）；
  - 需要区分 URL：许可证端点回 `{success:true}`，更新端点回「当前版本已是最新」，
    其余（`file://` 资源加载等）原样透传。
- 何时重新审视：上游换掉 `electron-fetch` 或不再用 `electron.net` 时。

## ADR-005：单一 CLI 入口 + 标志位，而不是一堆脚本

- 日期：2026-09-27
- 状态：已采纳
- 背景（遇到了什么问题）：
  仓库早期有 `analyze` / `activate` / `trial-reset` / `server` / `patch` / `build` 六个脚本，
  职责重叠、状态互相依赖，使用者不知道该跑哪个，且其中的实现（网关、字节码分析）已被证伪。
- 考虑过的方案：
  1. 保留多脚本，各自维护；
  2. 收敛成一个 `pnpm hack`，把回滚/状态/验收做成同一命令的标志位。
- 决策：采用方案 2。
- 为什么选这个：
  - 使用者要的动作只有一个：激活；回滚与状态是同一件事的周边，用标志位表达成本最低；
  - 单文件编排让「备份 → 注入 → 打包 → 写注册表 → 验收」的顺序无法被误用。
- 为什么不选其他：
  - 多脚本会诱导使用者跳步执行（比如只跑 patch 不写注册表），产生「打了补丁却没激活」的困惑。
- 后果：
  - `--restore` 与 `--status` 必须在文档里明确写出，否则会被当成不存在；
  - 已被证伪的实现整体删除，相关知识沉淀进 `docs/researches/` 与本文档。
- 何时重新审视：需要支持的平台变多、或需要批量部署时。

## ADR-006：把补丁做成版本无关 + 失败自动回滚

- 日期：2026-09-27
- 状态：已采纳
- 背景（遇到了什么问题）：
  第一版把 `launch.dist.js`、`atom.compiled.dist.jsc`、注入点字符串全部写死在代码里，
  并且把「补丁后文件头不变」当作自校验的识别判据。这在 1.14.10 上能跑，但换个版本就可能静默失效，
  而且失效的表现是「Typora 启动 1 秒后自己退出」——用户很难判断发生了什么。
- 考虑过的方案：
  1. 逐版本适配，在代码里维护一张版本 → 常量表；
  2. 把所有能推导的量都改成运行时/打包时计算，并对无法推导的部分加验收与回滚；
  3. 不改，靠文档提醒用户「只支持 1.14.10」。
- 决策：采用方案 2。
- 为什么选这个：
  - 能推导的量其实很多：入口名（包内 `package.json` 的 `main`）、自校验基准（打包时按实际内容算）、
    许可证里的版本号（同上的 `package.json`）、机器指纹（MachineGuid）；
  - 注入位置改为「文件最前面（`"use strict"` 之后）」后，完全不依赖入口里的任何语句形式，
    连「找到 jsc 的 require 语句」这一步都省掉了；
  - 真正推不出来的只有两项：伪造许可证的**字段名**与**接口路径**。它们无法从安装里推导，
    只能由启动验收兜底——一旦不匹配就把补丁撤掉，回到可用状态。
- 为什么不选其他：
  - 方案 1 需要为每个版本收集常量，维护成本随版本数线性增长，且新版本发布当天一定失效；
  - 方案 3 等于把问题推给用户。
- 后果：
  - `pnpm hack` 默认会启动 Typora 验收（约 10s），`--no-verify` 可跳过；
  - 验收发现「补丁导致的失败」时自动 `--restore` 并清空注册表，用户拿回一个完好的未激活 Typora；
  - 验收判定必须等过启动 ~1s 的自校验窗口：`hasL` 在 ~0.1s 就出现，而自校验在 ~1s 才跑完，
    只看到 `hasL` 就宣判成功会误报（这个坑实际踩过，日志里 `hasL: true` 与 `Integrity check failed`
    只差 900ms）；
  - 验收只读最后一次启动的日志片段：Typora 会轮转 `typora.log`，按文件长度切片会读到上一次运行的内容。
- 何时重新审视：上游把许可证载荷或接口路径改成与现在完全不同的形态，导致验收长期报失败时。
  **（2026-10-01 增补：ADR-012 把「版本无关」的定义收敛为「运行时发现 + 显式失败 + 自动回滚」——
  Mach-O 路线在符号表里现查补丁点，不携带任何指令偏移常量，与本条原则同构而非例外。）**

## ADR-007：邮箱与序列号放进 `.env`

- 日期：2026-09-27
- 状态：已采纳
- 背景（遇到了什么问题）：
  第一版把伪造许可证里的 `email` 与 `license` 直接写在补丁源码里，其中 `license` 还是从
  原机器上抓到的真实序列号——既有隐私问题，也让「伪造载荷」看起来像是复用了别人的凭证。
- 考虑过的方案：
  1. 留空，让 Typora 自己去填；
  2. 由入口内容哈希派生一个合成序列号；
  3. 从 `.env` 读，缺省用代码里的默认值。
- 决策：采用方案 3，同时保留「形状校验只警告不阻断」。
- 为什么选这个：
  - 实测确认 Typora 在**解密路径**上不校验 `email` / `license` 的内容，甚至不校验序列号的形状，
    所以这两个值纯属展示，交给用户配置既灵活又不会影响功能；
    （注意：**这不适用于 `fingerprint`**——它是硬校验，见 ADR-002 与研究报告 §4.1。）
  - 默认值写在代码里（`src/config.ts`），不配置也能直接跑通，符合「一条命令」的目标；
  - `.env` 不入库，用户的个人信息不会被提交。
- 为什么不选其他：
  - 方案 1 会让「我的许可证」对话框里出现空白字段，观感差；
  - 方案 2 生成的序列号是随机的，用户无法与自己记忆中的号码对应，出问题时不好核对。
- 后果：
  - `.env` 与 `.env.example` 分离：前者本地、后者入库作模板；
  - 优先级定为 `环境变量 > .env > 默认值`，符合一般直觉；
  - 序列号若不符合 `([A-Z0-9]{6}-){3}[A-Z0-9]{6}` 只打印警告——因为当前版本不校验，
    真遇到校验的版本会由启动验收兜住。
- 何时重新审视：若上游开始在解密路径上校验序列号内容（届时需要真正实现其校验位算法）。

## ADR-008：系统目录安装下，只提权「写文件」这一步

- 日期：2026-09-28
- 状态：已采纳
- 背景（遇到了什么问题）：
  Typora 默认装到 `%ProgramFiles%\Typora`，而 `BUILTIN\Users` 对该目录只有 `(RX)`。
  非管理员终端里 `pnpm hack` 会在「重新打包覆盖 app.asar」这一步失败。
  早期实现（本分支未提交的版本）走的是「检测到不可写 → 用 `Start-Process -Verb RunAs` 把整个 CLI
  重跑一遍」，实测有一串问题：`npx tsx` 与项目实际使用的 pnpm 不一致、`process.cwd()` 一旦不是仓库根就找不到脚本、
  参数没加引号、`cmd /k` 让父进程立刻以 0 退出（退出码是假的），而且**Typora 会以管理员身份被启动和验收**。
- 考虑过的方案：
  1. 整个 CLI 提权重跑（上面的现有实现）；
  2. 只把「写安装目录」这一步提权：解包/注入/打包全在临时目录做，最后一次性把备份与成品复制进去；
  3. 不自动提权，让用户自己开管理员终端。
- 决策：采用方案 2，用一次 UAC 完成批量复制。
- 为什么选这个：
  - 需要管理员的动作只有「往安装目录写文件」；把它隔离出来之后，其余流程的权限语义不变——
    注册表是 `HKCU`、日志在 `%APPDATA%`、Typora 以普通用户身份启动；
  - 提权窗口只跑一个临时 `.cmd`（内部两条 `copy`），不依赖 `pnpm` / `npx` / `tsx` 是否在 PATH 上，
    也不依赖 CLI 是怎么被调起来的；
  - `-Wait` 等它真正退出，成败由 `.cmd` 自己留下的标记文件判定（`-Verb RunAs` 下 PowerShell 的
    退出码不可靠），因此父进程的退出码是真实的；
  - 批量做，所以备份与成品只弹**一次** UAC。
- 为什么不选其他：
  - 方案 1 的每个问题都要单独打补丁，且「以管理员身份运行 Typora」这件事本身没法消除；
  - 方案 3 把失败留给用户，违背「一条命令」的目标。
- 后果：
  - `app.asar` 与备份的写入统一经过 `typora.ts` 的 `installFiles()`，`backup()` / `restore()` 两个直写函数被删除；
  - 因为要提权，`doHack` 的「备份」与「落盘」被拆成两步：先只判定备份状态（`planBackup`），
    落盘和成品打包在最后一次提权里一起完成；
  - 提权只在检测到不可写时发生，用户级安装（`%LOCALAPPDATA%`）全程无 UAC；
  - 目标目录可写时会直接 `copyFileSync`，复制被拒（ACL 判断偏差）时才自动退到提权一次。
- 何时重新审视：Typora 改成用户级安装、或 Windows 引入不需要提权的等价机制时。

## ADR-009：安装目录探测改为「多来源候选 + 惰性命中即止」

- 日期：2026-09-29
- 状态：已采纳
- 背景（遇到了什么问题）：
  原实现只探测三个固定目录（`%ProgramFiles%\Typora`、`%ProgramFiles(x86)%\Typora`、
  `%LOCALAPPDATA%\Programs\Typora`）。Typora 装在 D 盘或绿色版解压目录时直接报「未找到 Typora 安装」，
  而用户除了重装到默认位置之外无路可走。
- 考虑过的方案：
  1. 只加一个 `--dir` 参数，让用户自己指路径；
  2. 在固定目录之外补一个「全盘扫描」；
  3. 多来源候选（显式指定 → 注册表 App Paths/文件关联 → PATH → 默认目录 → 卸载表 → 全盘浅扫描），
     惰性求值、命中即止，同时保留 `--dir` 作为最高优先级的逃生舱。
- 决策：采用方案 3。
- 为什么选这个：
  - 注册表 `App Paths` / 文件关联 / 卸载表 `InstallLocation` 是官方安装器自己写下的，最可靠，
    而且每台机器至多几次 `reg query`，成本几乎为零；
  - 全盘扫描代价最大（要遍历目录树），因此排在最后，且**惰性触发**——前面的来源一旦命中就不跑；
  - 所有来源只产出「候选目录」，最终一律以该目录下存在 `resources\app.asar` 为准，
    与后续解包步骤用的判据完全一致，因此误报为零（候选对了才用，错了就跳过）。
- 为什么不选其他：
  - 方案 1 把问题推回给用户，违背「一条命令」的目标；
  - 方案 2 在 Typora 装在默认位置时也会先跑一遍全盘扫描，白白变慢。
- 后果：
  - 显式指定的目录无效时**直接报错、不回退**：显式意图优先于任何猜测；
  - 探测顺序严格按成本排序，失败信息里列出已尝试的来源，用户知道该往哪查；
  - 全盘扫描做了深度（≤3）与目录数（≤20000）双重上限，并跳过 `Windows` / `AppData` /
    `$Recycle.Bin` 等噪声目录，避免在超大目录树上卡死；
  - 实现上踩到两个 Windows 细节并已按判据固化：`reg query /ve` 的默认值标签在中文系统是「(默认)」
    而非「(Default)」（解析不得依赖标签文案）；查询不存在的键是常态，其 `stderr` 必须静默，
    否则会污染用户终端。
- 何时重新审视：Typora 改成把安装位置写进某个统一入口、或提供官方的定位接口时。

## ADR-010：平台差异下沉到 src/platform/，未实现的能力显式失败

- 日期：2026-09-29
- 状态：已采纳
- 背景（遇到了什么问题）：
  需要支持 macOS（arm64）与桌面 Linux（Ubuntu / Fedora / Arch）。一开始的判断是「只有找包的逻辑不一样，
  其余通用」，但核对代码后发现至少六处随平台变：定位安装目录、进程检测/结束、启动、验收日志路径、
  写入安装目录（提权）、许可证存储。其中补丁本身确实通用（`publicDecrypt` hook、`electron.net` 拦截、
  fs/crypto 自校验放行都与平台无关），可**存储**这一层是硬差异：Windows 用 `HKCU\SOFTWARE\Typora`，
  而 macOS / Linux 的落点（文件 / plist / keychain）没有任何实证结论 —— 日志里的类名 `[WindowsLicenseLocalStore]`
  本身就说明每个平台一套实现，公开情报则指向 macOS 可能走 plist/Keychain。
- 考虑过的方案：
  1. 在 `hack.ts` 里按 `process.platform` 到处分支；
  2. 抽一层 `Platform` 接口，把六件事下沉到 `src/platform/<id>.ts`；
  3. 不抽层，先把 Windows 做完，跨平台以后再说。
- 决策：采用方案 2；且**许可证存储未实现的平台，在改动任何文件之前直接失败**。
- 为什么选这个：
  - 方案 1 会让平台判断散落各处，加一个平台要改遍流程，且极易漏；
  - 方案 2 让「加一个平台」= 加一个文件 + 一行分支，编排流程完全不动，也让平台行为可单独测试；
  - 许可证存储是唯一没有实证结论的部分。**猜一个位置写进去的代价远大于失败**：猜错会产出
    「打了补丁却没激活」的状态，日志里没有任何错误，用户与维护者都要花大力气定位；
    显式抛错则一眼看出原因，而且因为发生在改动文件之前，Typora 仍是完好的。
- 为什么不选其他：
  - 方案 3 等于让第一个非 Windows 用户去撞一整面墙，而这些墙本可以现在就拆掉。
- 后果：
  - `src/typora.ts` 退化为平台无关门面；`src/registry.ts` 只被 Windows 实现使用；
  - `hack.ts` 不再出现平台分支，只在平台选择失败（不支持的 OS）时报错退出；
  - Unix 提权用 `sudo -n`（非交互）：需要密码时立刻失败并提示先 `sudo -v`，绝不挂住 CLI；
  - macOS / Linux 上 `--status` 与 `--restore` 仍可用（它们不需要写入许可证）；
  - 验收日志路径在 macOS / Linux 上是按 Electron userData 惯例推断的，**未在真机验证**，
    实现里已显式标注；
  - macOS 还有两项未验证的风险：Electron 的 asar integrity（Info.plist 内嵌 app.asar 哈希）
    与代码签名，若启用则改写 app.asar 会导致启动失败。落地前须在 arm64 真机上确认。
- 何时重新审视：拿到 macOS / Linux 上许可证存储的实证结论后，补上 `writeLicense`；
  或在 arm64 真机上确认 asar integrity 会阻断改写时，重新评估 macOS 的可行性。
  **（2026-10-01 更新：macOS 部分的假设已被真机实证推翻并按 ADR-011 落地，本节其余结论仍然有效。）**

## ADR-011：macOS 版是原生应用，改走「伪造许可证记录文件」路线

- 日期：2026-10-01
- 状态：**路线选择已被 ADR-012 取代**（本 ADR 的机制实证结论——原生结构、记录文件格式、
  密钥派生、续期机制——仍然有效并继续被 ADR-012 引用）
- 背景（遇到了什么问题）：
  ADR-010 预设 macOS 版 Typora 与 Windows/Linux 同为 Electron 结构，只是许可证存储位置未知。
  在 arm64 真机（Typora `1.14.5-dev`）上核对后发现**整个前提是错的**：macOS 版是原生
  ObjC/AppKit + WKWebView 应用——没有 app.asar、没有明文入口、Frameworks 里只有 Sparkle，
  许可证逻辑全在 Mach-O 的 `LicenseManager` 类里。Windows 的「注入 asar」路线在 macOS 上
  没有任何落点，且包有 Developer ID 签名 + hardened runtime + Sealed Resources，
  改写包内任何文件都会破坏签名。
  （完整实证见 `docs/researches/activation-mac.md`；附带发现：现有 `locate` 以「存在 asar」为判据，
  在 macOS 上连 Typora 都找不到。）
- 考虑过的方案：
  1. **伪造许可证记录文件**：逆向出 `~/Library/Application Support/<bundle id>/.<fingerprint>`
     的格式（AES-256-CBC 加密的 NSKeyedArchive），直接写一个合法的「已激活」记录；
  2. 二进制 patch：反汇编定位 `hasLicense` / `quickValidateLicense:`，改指令后 ad-hoc 重签名；
  3. DYLD 注入：利用 entitlements 里的 `allow-dyld-environment-variables` 注入 hook 库。
- 决策：采用方案 1。macOS 上 **hack 不触碰 /Applications**，只改写 `~/Library` 下的许可证记录；
  `Platform` 增加 `asarPatchSupported` 能力位，`hack.ts` 按能力位（而非平台名）分支。
- 为什么选这个：
  - 方案 1 的机制基础已全部实证：密钥派生（`SHA256(IOPlatformUUID + "typora-license")`）、
    加密形态（AES-256-CBC、零 IV、PKCS7）、文件结构（keyed archive）、指纹命名
    （`Base64(SHA256(IOPlatformUUID))[0..10]` 清洗）、启动判定（只要 `email`/`license` 键非 nil）
    与续期窗口（`lastTry` 距今 `[1,12)` 小时内不续期）都能在本地复现；
  - 不动安装目录 ⇒ 无提权、无 App Management TCC、不破坏代码签名、Typora 升级不覆盖伪造
    （升级后首启会强制续期一次，重跑 hack 即恢复，见「后果」）；
  - 方案 2 与 ADR-006「版本无关」直接冲突：指令寻址随版本漂移，且重签名会破坏 Sparkle 更新；
  - 方案 3 被 library validation 挡死：entitlements 有 `allow-dyld-environment-variables`，
    但没有 `disable-library-validation`，注入非同 Team ID 的 dylib 会被内核拒绝。
- 为什么不选其他：
  - 方案 2 的每次 Typora 升级都要重新逆向一遍指令位置，维护成本与「一次命令激活」的目标相悖；
  - 方案 3 需要请求开发者签名或关闭 SIP，都不在可接受范围内。
- 后果：
  - `hack.ts` 引入 `asarPatchSupported` 分支：asar 路线（备份/注入/打包/提权）只在
    Windows/Linux 执行；macOS 走「备份记录文件 → 伪造 → 验收」；
  - `Platform` 新增 `probeActivation`：Windows 读 `typora.log` 关键字，macOS 轮询记录文件是否
    仍带激活键（unfill 会把记录物理清写）+ 进程存活——macOS 上没有可用的日志通道
    （不存在 `typora.log`，unified log 在启动路径无输出，已实测）；
  - 许可证存储有两套实现：Windows 注册表 + macOS 加密记录文件；Linux（Electron 版）仍显式失败；
  - **已知限制（激活有效期）**：防线是 `lastTry` 窗口，关机的机器距上次 hack 超过 12 小时后
    重启会触发续期，服务器对伪造序列号返回 `success=false` 会导致 unfill，需重跑 `pnpm hack`；
    若 `.env` 里配的是真实有效的序列号，续期成功则不受此限；
  - 记录文件的编码有两条硬约束（int marker 宽度、`NS.time` 必须 real），
    踩错时 `NSKeyedUnarchiver` 会静默返回 nil（现象是「伪造被无视、状态未激活」且无报错），
    已固化为研究报告 §2.3 与生成器的实现约束。
- 何时重新审视：Typora 在 macOS 上改记录文件格式/密钥派生，或收紧续期窗口（届时验收会
  以「记录被清除」显式失败并回滚）；或需要面向长时间不联网的机器时，评估常驻刷新组件。

## ADR-012：macOS 改走「Mach-O 二进制补丁」路线，对齐 Windows 的永久激活语义

- 日期：2026-10-01
- 状态：已采纳（取代 ADR-011 的路线选择；其实证结论继续有效）
- 背景（遇到了什么问题）：
  ADR-011 的记录路线在实测中暴露出与 Windows 路线**语义不对齐**的硬伤：激活有效期
  等于 `lastTry` 续期窗口（伪造值 `now−2h` 落在 `[1,12)` 小时不续期窗口内），距上次
  hack 约 10 小时后的任何一次启动都会真的向 `{store.typora.io | dian.typora.com.cn}/api/client/renew`
  发请求，服务器对伪造序列号回 `success=false` ⇒ `unfillLicense` 把记录物理清空——
  静默失效、无任何报错。Windows 路线（asar 注入伪造 renew 响应）则是一次激活永久有效。
  维护者决策：效果必须对齐 Windows，**修改二进制**。
- 考虑过的方案：
  1. 维持记录路线 + 常驻刷新组件（定时重写 lastTry）：违背「不引入任何常驻组件」的产品目标；
  2. 网络层拦截（hosts/DNS 拦下 renew 域）：PRD 明确排除，且影响面超出 Typora；
  3. **Mach-O 二进制补丁**：在 `-[LicenseManager renew]` 的 IMP 首指令写 `ret`（arm64
     `c0 03 5f d6` / x86_64 `c3`，等长替换），ad-hoc 重签（entitlements 原样保留 +
     追加 `disable-library-validation`），记录伪造保留（启动判定仍读记录）。
- 决策：采用方案 3。`Platform` 新增 `machoPatchSupported` 能力位（三路线能力位模型），
  darwin 实现 = `darwin-macho.ts`（解析/补丁/重签/备份事务）+ 记录伪造不变。
- 为什么选这个（对 ADR-011 两条否决理由的实证反驳）：
  - 「指令寻址随版本漂移、与 ADR-006 版本无关冲突」——实测（1.14.5-dev）二进制**未剥离
    本地符号**，两个架构的符号表都直接给出 `-[LicenseManager renew]` 的 IMP 地址；
    程序化定位 = 解析 fat 头 → `LC_SYMTAB` 精确匹配符号名 → 按段包含性映射文件偏移，
    **零硬编码偏移**，与「读 package.json 的 main」同构。补丁是等长的单指令替换，
    后续偏移不漂移；符号缺失时写盘前显式失败（宁失败不猜，正是 ADR-006 的精神）；
  - 「重签名会破坏 Sparkle 更新」——属实，但**被接受且反转为收益**：Sparkle 应用内自动
    更新失效 = 补丁不会被自动更新静默替换，与 Windows 路线「伪造更新检查使 asar 不被
    替换」语义等价。需要升级时手动下载覆盖，然后重跑 `pnpm hack`（备份状态机识别为
    refreshed 自动刷新备份）；
  - 补丁目标选 `renew` 而非 ADR-011 设想的 `quickValidateLicense:`（它只在手动输码流程，
    不在启动路径）：短路 renew 即断掉唯一会把激活打回的路径，且根本不发网络请求，
    比 Windows 的「伪造成功响应」更强（零回连）。
- 为什么不选其他：
  - 方案 1 与「一条命令、无常驻」的产品目标直接冲突；
  - 方案 2 是 PRD 非目标，且改 hosts 影响整机其他流量。
- 后果：
  - **激活永久有效**：renew 永不运行 ⇒ unfill 不可达 ⇒ 伪造记录永不过期。失效仅剩
    「手动重装/升级 Typora」一种，重跑 `pnpm hack` 即恢复；
  - **`lastTry` 改为金丝雀（`now − 48h`，窗口外）**：补丁生效时此值不参与判定；窗口外
    记录存活本身就是「renew 已被中和」的自证（每次 hack 验收自动证明补丁生效），
    补丁失效时下一次启动立刻可见地被打回而非 10 小时后静默过期；
  - ad-hoc 重签的代价（如实记录）：原始 Developer ID 签名让位（`--restore` 逐字节还原
    即自愈回原始签名）；`disable-library-validation` 使该应用对本机 dylib 注入的抵抗力
    下降（本机权衡，完全可逆）；macOS 13+ 首次改包触发一次 TCC「App Management」弹窗；
  - 备份在包外（`<app>.hapora-orig.bak/`，二进制 + CodeResources + entitlements + manifest，
    哈希是唯一身份、偏移仅诊断）；还原 = 字节等价拷回，无需再签；
  - **重签会重排胖文件布局**：一切字节复核对重签后的磁盘文件重新解析定位（实测 arm64
    补丁点偏移 `0x2071f8` → `0x2031f8`），绝不缓存偏移；
  - 安装 staged 文件必须显式恢复执行位（`copyFileSync` 沿用源的 mode，此坑真机踩过）；
  - 提权探测点从记录文件改为二进制所在目录（记录文件恒可写，探它会误判无需提权）。
- 验收（2026-10-01 真机 · macOS arm64 / Typora 1.14.5-dev，判据全文见
  `docs/specs/module-hack-cli.md`）：ret/retq 双架构首指令、adhoc + strict verify +
  4 项 entitlements、窗口外 lastTry 记录存活、还原后 Developer ID 签名自愈且逐字节一致、
  双跑幂等——全部通过。
- 何时重新审视：Typora 发布剥离符号的版本（届时显式失败并需重新逆向定位方法，
  见研究报告 §10.2）；或上游把许可证逻辑重命名/重构导致符号消失。
